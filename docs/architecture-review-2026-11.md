# 重构复核与目标架构（2026-11）

复核范围：`9485fa4`（v1.5.1 发布）之后的 65 个提交。

## 一、复核结论

**已站住的部分（保留）**

| 提交 | 产出 | 为什么保留 |
| :--- | :--- | :--- |
| `d5cfc07` | 移除 `Deref`，1887 处访问显式化 | 纯 API 收紧，无运行期风险 |
| `6cdb7e9` | `AppSettings` 进 `Global` | 配置不挂外壳，消掉 300+ 处穿透 |
| `c9b55e7` | `MonitorView` 实体 | 状态与渲染有归属，按面板重绘 |
| `9eed0dd` | `EditorPanels` 实体 | 同上 |
| `dd9e50d` | `ForwardView` 实体 | 同上，表单校验归面板 |
| 各面板的 `widgets` 收敛、门禁与守卫 | — | 与架构无关的正向收益 |

**结构上没解决、必须重做的部分**

1. **外壳仍是单体**：65 个提交后 `AppShell` 仍有 **549 个方法**。搬走的是面板，没搬走的是"窗口根承担一切"这个结构。
2. **面板持有父引用并同步回调**：4 个面板实体都带 `WeakEntity<AppShell>`，配 3 套回交通道：

   | 通道 | 使用点 | 引入者 |
   | :--- | ---: | :--- |
   | `with_shell` | 40 | monitor / editor / forward |
   | `with_shell_parts` | 21 | sftp |
   | `read_shell_parts` | 28 | sftp |

   共 89 个运行期可能成环的调用点。两次线上 panic 全部出自这里。
3. **协议不统一**：同一件事（面板要外壳发命令）在四个面板里有三种写法。没有统一协议，就无法写守卫、无法评审、无法阻止回归。

**一句话结论**：状态实体化做对了，**通信协议做错了**；继续按现在的路子往下做，只会把 89 个点变成更多点。要的是换协议，不是继续搬。

## 二、根因

GPUI 实体单租借。`AppShell` 时代所有调用都是 `&mut self`，借用检查器在编译期兜住；
实体化把"对象内调用"改成"对象间调用"，而**跨实体调用不在借用检查范围内**。

只要允许"A 持有 B 的句柄并同步回调 B"，环就随时可能出现。修补只能让已知的环消失，
不能阻止新的环出现。

## 三、目标架构

### 所有权与调用方向

```
AppShell（窗口根）
├─ 持有：services / 命令通道 / store / persistence / tasks / 布局尺寸
├─ 渲染：把子实体按句柄挂进布局树
├─ 接收：子实体事件（订阅），转成命令投递 / 弹窗 / 生命周期操作
└─ 不再：持有任何"面板内部状态"，不再调用面板方法做跨域动作

面板实体（MonitorView / EditorPanels / SftpPanelView / ForwardView）
├─ 持有：自己那份状态
├─ 渲染：只读自身状态 + Global（设置）
├─ 接收：外壳推下来的数据（连接号、会话规则、采样快照…）
└─ 发出：意图事件（发命令 / 开弹窗 / 请求关闭 / 调整宽度）
```

**方向铁律**

- 数据 **只向下**：外壳 → 面板（`update` 注入）
- 意图 **只向上**：面板 → 外壳（`emit` 事件）
- 面板 **不持有** `WeakEntity<AppShell>`；外壳 **不读** 面板内部字段做业务判断

### 协议定义

```rust
pub(crate) enum PanelEvent {
    SendCommand(SftpCommand | ForwardCommand | HostCommand),
    OpenModal(ModalRequest),      // 参数随事件携带，父不反查
    ClosePanel,
    RequestWidth(f32),
}
```

三条约束：

1. 事件必须**自带全部数据**。父的处理函数只用事件内容，禁止 `view.update(...)` 回读。
2. 父的处理函数运行在事件派发阶段（子实体已释放租借），可以放心 `send_command` / 开弹窗。
3. 面板渲染不得反查外壳。渲染所需外部数据由外壳在变化时推送（采样、连接、规则变更都是低频事件，推送成本可忽略）。

### 外壳的收敛

外壳保留三类东西，其余全部下沉：

| 保留 | 下沉到 |
| :--- | :--- |
| 布局与面板挂载、尺寸 | — |
| 事件路由（面板事件 → 命令/弹窗/生命周期） | — |
| 服务持有（命令通道、store、后台任务） | — |
| 标签与窗格生命周期 | 不再细分（本就是窗口根职责） |
| 面板状态（sftp 队列、编辑缓冲、转发规则表单…） | 各自面板实体（已完成） |
| 配置 | `Global`（已完成） |

## 四、迁移路线（每步可独立验收）

**M1. 定义协议与样板链路**

- 新增 `panel_event.rs`：`PanelEvent` + `ModalRequest`
- 只改一条链路：SFTP「删除文件」——面板 `emit(SendCommand)`，外壳订阅后投递
- 验收：删除文件可用；`sftp` 下该链路不再出现 `with_shell_parts`

**M2. SFTP 去父化（49 点）**

- 按类型替换：发命令/开弹窗 → `emit`；取外壳数据 → 外壳推送注入
- 删除 `SftpPanelView.app`、`with_shell_parts`、`read_shell_parts`
- 验收：SFTP 全功能手测；守卫测试通过

**M3. 其余面板去父化**

- monitor：采样数据由外壳推送（`set_stats`），渲染不再 `active_stats` 反查
- editor：设置走 `Global`，关闭闸门等跨域动作改 `emit`
- forward：会话规则/状态由外壳在变更时注入
- 删除 `with_shell`（40 点）

**M4. 外壳收敛**

- 按 `sftp` 68 / `settings` 74 / `editor` 31 / `monitor` 22 的既存分类，把"面板专属动作"下沉到面板实体，只留事件处理
- 目标：`AppShell` 方法数降到 200 上下（Zed `Workspace` 364，但它包含完整的标签/窗格/面板编排）

**M5. 守门与收尾**

- 守卫测试三条：面板结构体无 `WeakEntity<AppShell>`；面板目录无 `with_shell*`；外壳事件处理函数不出现 `view.update(` / `sftp_view(`
- 删除 `with_shell*` 三个通用通道与相关文档
- AGENTS 写入最终协议

## 五、明确不做

- 不用 `cx.defer` 兜底（`'static` 约束 + 时序漂移）
- 不把面板退化成纯视图（等于回退实体化）
- 不为了方法数强行拆 `workspace`/`tabs`（窗口根职责，拆分只会制造假边界）

## 六、风险与验收

| 风险 | 缓解 |
| :--- | :--- |
| 事件携带数据变多，定义啰嗦 | 用 `ModalRequest` / `Command` 枚举收敛，不散落结构体 |
| 推送遗漏导致面板显示旧数据 | 每个推送点在数据变更处显式调用，测试覆盖"变更后一帧内一致" |
| 迁移期新旧协议共存 | 按面板逐个完成，每个面板完成后守卫测试即锁死，不允许混用 |
